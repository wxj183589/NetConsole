# 轨道交通业务规则

本文档记录轨道交通、AC / FIT-AP、轨旁 AP、车内通信、MR Mesh 和车载 MR 采集分析的长期规则。

## 总体原则

- 轨道交通规则必须通用，不写死局点、线路、站点、AP、车号、MAC、IP。
- PIS 场景是重点，但代码不能只服务某个项目截图。
- 信号系统可能存在红网/蓝网；PIS 通常没有红网/蓝网，不能混用规则。
- AP 扩展信息和点位规划与局点、站点、线路设计表有关，每条线路格式可能不同。

## 轨旁 AP 业务

### 数据和识别

- 轨旁 AP 业务依赖设备管理、AC FIT-AP 资源、FIT-AP 光衰、交换机接口/LLDP/光模块数据和 AP 扩展信息。
- AP 扩展信息可能来自原始设计表、布点表或 AP 名称+MAC 清单。
- PIS 表可能包含曲线半径、曲线开始、曲线终点等字段，这些会影响 AP 部署间距和 RSSI 评估。
- AP 间距、Wi-Fi 5/6、频宽 20/40/80M、PIS/信号业务差异都会影响阈值，不能使用单一固定模板。

### 光衰规则

- 交换机侧、AP 侧光衰判断复用现有阈值和状态规则。
- AP 侧和交换机侧异常颜色/状态应一致复用。
- 导出不依赖 WPS/Excel 客户端筛选，必须程序自动生成。

### 导出规则

轨旁 AP 业务导出 xlsx 包含主 sheet“轨旁AP业务”。其后应紧跟“当前异常光衰”sheet。

“轨旁AP业务”固定列序为：归属站点、室内交换机、接口名称、Link、室内交换机收光(dBm)、交换机模块状态、AP_MAC、AP名称、AP侧收光(dBm)、AP设备模块状态、AP业务光衰、最后采集时间、交换机侧光衰变化、AP侧光衰变化、AP业务门限、AP业务判定原因。该顺序只约束导出，不改变 Web 页面列序。

主 sheet 的整行背景色只用于有 AP 业务依据的状态：

- 交换机侧为无光模块时不填充背景色，即使 Link 为 DOWN。
- 交换机侧为无光且没有当前或历史 AP 证据时不填充背景色。
- 有当前 LLDP、历史 LLDP、FIT-AP 资源、AP UUID、AP MAC 或 AP 名称任一证据的无光端口仍按真实业务异常着色。
- 正常、预警和真实光衰/链路异常继续使用既有绿色、黄色和异常色。

“当前异常光衰”规则：

- 只导出当前光衰质量异常行。
- 无光且没有任何当前/历史 AP 证据的空闲端口不属于该 sheet。
- 无光模块、未插光模块、光模块不存在、DOWN 且 AP 信息为空的空闲端口，不属于该 sheet。
- 保留偏低关注、一般告警、严重告警等当前光衰异常。
- 主 sheet 保留完整数据，不因异常页筛选而删除无光行。
- 新 sheet 保留表头、列宽、样式、筛选和冻结窗格。
- 无数据时仍生成 sheet，并显示明确中文空状态。

“当前异常光衰”使用独立的 19 列契约：归属站点、室内交换机、接口名称、Link、室内交换机收光(dBm)、交换机模块状态、AP_MAC、AP名称、AP侧收光(dBm)、AP设备模块状态、AP 在线状态、异常侧、异常等级、异常原因、最后采集时间、交换机侧光衰变化、AP侧光衰变化、AP业务门限、异常说明。不重复导出 AP业务光衰、AP业务判定原因或光衰判定；异常等级和异常说明分别是唯一的严重程度和完整说明字段。

## 车内通信检测系统

目标：

- 检测对象是车内有线通信链路。
- 重点关注车载 MR 到车内设备、TC1/TC2 跨 TC 通信、对端 MR 或对端车内关键 IP。
- 地面到车载 MR 不通是正式环境常见情况，车辆可能下电或射频关闭，不直接判定车内网络故障。

规则：

- 单端 MR 在线是正式环境常见情况。
- 只要单端 MR 登录后可以 ping 通对端 MR 或对端车内关键 IP，即可判断车内通信链路可用。
- 快速检测周期统一 4 秒，用于快速判断链路状态。
- 快速检测后单独执行跨 TC ping，用于判断跨 TC 是否丢包。
- VRRP 下方跨 TC 线条：绿色正常、黄色丢包、红色不通。
- 列车列表必须按列车号自然数字升序排序；不能按插入顺序、更新时间或字符串原始顺序。
- `1车` 与 `01车` 应等价参与排序；禁止固定 01~18 或某条线路。

主题约定：

- 车内通信检测页面必须完整适配亮/暗主题。
- 禁止在 `changeEvent` 中调用会 `setStyleSheet` 的 `apply_theme()`。
- 主题切换只更新视觉，不重建页面、不清空日志、不停止检测任务。

## MR 原始 MESH 日志分析

边界：

- MR 原始 MESH 日志分析与车载 MR 实时收集/收集分析不是同一种数据源，不能混淆。
- 原始日志、解析数据库、导出报告应分开保存。

规则：

- RSSI = 信号 - 底噪。
- 2.4G 底噪通常按 -95，5G 底噪通常按 -105，图表显示可用正值。
- mesh-log 默认约 1 秒采样。
- 关键字段包括 Radio、LinkState、PeerMac、EstablishTime、DurationTime、LinkCnt、L/P_Rssi、L/P_Cpu、L/P_Mem、L/P_TxBusy、L/P_RxBusy 等。
- 分析重点关注 ACTIVE，通常不重点关注 STANDBY。
- 图表应支持滚轮缩放、拖动、tooltip、点击采样点和中文提示。
- 大数据要分页、抽样、懒加载或数据窗口，避免卡顿。
- 报告高级阈值窗口中的 QSpinBox / QDoubleSpinBox 不得被鼠标滚轮误修改。

### H3C AP MAC / Radio MAC 映射

- AP MAC 与 Radio MAC 先规范化为 12 位十六进制。
- Radio 1：Radio MAC 与 AP MAC 前 11 位一致。
- Radio 2：Radio MAC 与 AP MAC 前 10 位一致，且第 11 位按十六进制比 AP MAC 第 11 位大 1。
- Radio 2 的第 12 位不要求与 AP MAC 一致。
- 禁止用具体 MAC 写死匹配。

## 车载 MR 实时收集 / 收集分析

初始化命令顺序：

```text
screen-length disable
terminal logging level 7
terminal monitor
system-view
user-interface vty 0 31
idle-timeout 1440 0
return
```

采集内容：

- 主链路：`display clock` + `display wlan mesh-link`
- 信道繁忙度：`display ar5drv 1 channelbusy`，射频口按配置。
- AP 射频统计：`display ar5drv 1 statistics`
- 主链路切换历史：`display wlan mesh-link switch-history`
- 接口流量：`dis counters rate inbound/outbound interface`
- fping 丢包。
- iperf3 打流数据，如存在。

分析图表：

- 全部使用动态交互图表。
- 支持 tooltip、点击详情、缩放、拖动、图例开关。
- RSSI、信道繁忙度、丢包、接口流量、打流数据使用统一时间轴。
- 主链路切换点需要标记。
- 无打流数据时显示“当前会话无打流数据”，不报错。

## 当前实现与待统一事项

- 轨道交通下具体子页随功能开关和构建 profile 可能隐藏或禁用；文档描述的是完整能力边界。
- 阈值模板需要根据业务系统、频宽、AP 间距和现场规则持续校准，不应写死单一现场模板。
