# Electron-only E6 数据库访问调优归档

## 结论

2026-07-18 对开发数据根中的 398 个 SQLite 数据库完成只读分类，并重点检查 `devices.db`、`tasks.db`、`agents.db`、`traffic_runs.sqlite`、`iperf_results.sqlite`、Online MR 与 MESH 数据库。Task、Agent、Traffic、iPerf 和 MESH 的主要过滤/时间查询已有索引，本阶段不修改这些 schema；Online MR 代表库数据量较小，也不为形式统一强行迁移。

`devices.db` 的 7 类历史查询在真实数据库的 SQLite Backup 临时副本中均表现为全表扫描并创建临时排序树，因此增加 7 个只改变访问路径、不改变字段或事实含义的复合索引。

## 证据

审计代表库约 409.8 MB，`PRAGMA quick_check=ok`。以下数据使用相同 SQL、相同参数、相同 100 行限制，对系统临时目录中的无覆盖 SQLite Backup 副本测得：

| 查询 | 整改前中位数 | 加索引后中位数 | EXPLAIN 变化 |
| --- | ---: | ---: | --- |
| 设备接口历史 | 45.652 ms | 0.187 ms | `SCAN + TEMP B-TREE` → 复合索引搜索 |
| 设备光模块历史 | 28.462 ms | 0.263 ms | `SCAN + TEMP B-TREE` → 复合索引搜索 |
| 设备 LLDP 历史 | 18.319 ms | 0.131 ms | `SCAN + TEMP B-TREE` → 复合索引搜索 |
| FIT-AP 资源历史（按 AC） | 101.773 ms | 0.140 ms | `SCAN + TEMP B-TREE` → 复合索引搜索 |
| FIT-AP Radio 历史（按 AP） | 27.139 ms | 0.164 ms | `SCAN + TEMP B-TREE` → 复合索引搜索 |
| FIT-AP LLDP 历史（按 AP） | 30.411 ms | 0.206 ms | `SCAN + TEMP B-TREE` → 复合索引搜索 |
| FIT-AP 光衰历史（按 AP） | 33.537 ms | 0.391 ms | `SCAN + TEMP B-TREE` → 复合索引搜索 |

没有为返回 100000 行的全量导出查询追加专用索引：实测仅提高约 1.6–1.8 倍，耗时主要来自大量行物化，且导出已在后台进程运行，继续增加索引会扩大写入和磁盘成本。

## Schema 变更

主库 schema 版本更新为 `2026.07.18.history_query_indexes`，新增：

```text
idx_device_interfaces_history_device_interface_time
idx_device_optical_history_device_interface_time
idx_device_lldp_history_device_interface_time
idx_fit_ap_resource_history_ac_time
idx_fit_ap_radio_history_ap_time
idx_fit_ap_lldp_history_ap_time
idx_fit_ap_optical_history_ap_time
```

索引全部使用 `CREATE INDEX IF NOT EXISTS`，由现有 `Database.initialize()` 对新库和旧库幂等应用。旧库副本迁移实测约 1052.5 ms，增加约 88.3 MB；四类代表表行数完全保持，schema 版本正确，`quick_check=ok`，查询计划命中新索引。

## 兼容与回滚

- 不删除表、字段、行或旧索引，不改变 Repository API、字段语义、排序和分页结果。
- 建索引在现有初始化事务边界中执行；失败不会以新 schema 版本标记完成，下次初始化可幂等重试。
- 如需回滚性能变更，可在已备份数据库上逐项 `DROP INDEX`，旧代码仍可读取同一 schema；通常无需回滚数据。
- 本阶段没有启动真实 Electron，因此没有对活动开发数据库执行写入；真实升级将在用户下一次启动相应局点数据库时完成。
